# Project 01 — Authentication Vulnerability Testing

##  Overview

This project is part of my hands-on web application penetration testing practice.

For this project, I used **OWASP Juice Shop** as the target application and focused specifically on authentication-related functionality.

The goal was not just to find vulnerabilities, but also to understand how authentication works, test the application's security controls, document the results, and understand how the issues could be fixed.

### Target

- **Application:** OWASP Juice Shop
- **Environment:** Local lab
- **Target URL:** `http://127.0.0.1:3000`
- **Testing Type:** Black-box Web Application Security Testing

### Tools Used

- Burp Suite Community Edition
- Web Browser
- OWASP Juice Shop
- Browser Developer Tools


---

#  Reconnaissance

I started the assessment by running OWASP Juice Shop locally and exploring the application like a normal user.

Before testing for vulnerabilities, I wanted to understand which parts of the application were related to authentication and how the application communicated with its backend.

During the initial exploration, I identified the following functionality:

- User registration
- User login
- Forgot password
- Password reset
- User profile functionality
- Authentication-related API endpoints
- JWT-based authentication

I used Burp Suite to intercept the HTTP requests generated by the application. This allowed me to see which endpoints were being used and what information was being sent to the server.

### Reconnaissance Notes

The main areas I decided to focus on were:

1. Password requirements during registration
2. Login and authentication behavior
3. JWT token handling
4. Password-reset functionality

After identifying these areas, I moved on to manual testing.


---

#  Methodology

I used a black-box testing approach for this assessment.

I did not modify the source code of the application. Instead, I interacted with the application through the browser and inspected the HTTP traffic using Burp Suite.

For each test, I first observed the normal behavior of the application and then modified the relevant request to see whether the security controls could be bypassed.

My general testing process was:

**Discover → Intercept → Modify → Replay → Verify → Document**

The main authentication tests performed were:

- Registration and password policy testing
- Login testing
- JWT authentication testing
- Password-reset testing

I only considered an issue a confirmed vulnerability when I could reproduce it and demonstrate a real security impact.


---

# Authentication Testing

## 1. Registration Testing

I started with the registration functionality because password requirements are one of the basic controls protecting user accounts.

I created a test account and intercepted the registration request using Burp Suite.

I then tested different weak passwords to see whether the application would reject them or allow the account to be created.

One of the passwords I tested was:

`123`

### Request

The registration request was captured in Burp Suite and the password fields contained the weak password.


### Response

The server accepted the registration request and returned:

`HTTP/1.1 201 Created`


<img width="1712" height="839" alt="02-weak-password" src="https://github.com/user-attachments/assets/0c8c1ce7-2849-4634-b670-bcd5596111da" />

The account was successfully created even though the password was extremely weak.

This confirmed that the application was not enforcing an adequate password-strength policy during registration.


---

## 2. Login Testing

After creating the test account, I tested the login functionality using the credentials created during the registration test.

I captured the login request using Burp Suite and reviewed the request and response to understand how authentication was being handled.

I also inspected the authentication token returned after a successful login.

During this testing, I did not identify a separate login bypass that I could successfully reproduce.

Therefore, no login-bypass vulnerability was reported from this test.


---

## 3. JWT Authentication Testing

The application uses JWT tokens for authentication, so I also wanted to understand how the application handled these tokens.

I decoded the JWT header and payload and identified that the token was using the **RS256** signing algorithm.

I then tested whether modifying values inside the JWT payload could result in unauthorized access.

One of the values I tested was the user's role.

The original token contained:

`"role": "customer"`

I tested changing the role to:

`"role": "admin"`

<img width="1715" height="848" alt="jwt-testing" src="https://github.com/user-attachments/assets/1de57b6f-6d67-4c20-95e0-ecc2f1bfbef8" />


I also tested invalid and modified tokens.

Although some modified-token requests returned `HTTP 200`, the response did not contain an authenticated user and returned an empty user object.

Because I could not demonstrate successful authentication or privilege escalation using the modified token, I did not report this as a confirmed vulnerability.

This was still useful as part of the assessment because it helped me understand the difference between receiving a successful HTTP response and actually bypassing authentication.


---

## 4. Password Reset Testing

I also tested the forgot-password and password-reset functionality.

I first went through the normal password-reset process and identified the requests related to the security question and password change.

I then tested invalid or modified requests using Burp Suite.

The application rejected the invalid attempts with:

`HTTP 401 Unauthorized`

<img width="1720" height="845" alt="password-reset" src="https://github.com/user-attachments/assets/14f8684f-ebbc-4a3e-9ddf-bd4df8ca2b04" />

Since I was unable to bypass the verification process or change an account password without the required information, I did not report a password-reset vulnerability.

This test helped confirm that the application was performing an authorization check for the invalid requests.

#  Findings

## AUTH-01 — Weak Password Policy

**Severity:** Medium

**Status:** Confirmed

### Description

During registration testing, I found that the application allowed users to create accounts using extremely weak passwords.

For example, I was able to register an account using:

`123`

The application did not reject the password because of its weak strength and instead processed the registration successfully.

### Proof of Concept

I intercepted the registration request using Burp Suite and submitted the following test data:

```json
{
  "email": "test11@gmail.com",
  "password": "123",
  "passwordRepeat": "123"
}
```

<img width="1712" height="839" alt="02-weak-password" src="https://github.com/user-attachments/assets/dea2a8ff-de7f-495d-8631-bee79593f859" />

# Impact
Allowing extremely weak passwords makes user accounts much easier to compromise through password guessing and brute-force attacks.

An attacker does not need to exploit a complicated technical vulnerability if users are allowed to protect their accounts with passwords that are very easy to guess.

The risk could become more serious if users reuse the same weak password on other services.

---

# Recommendation

The application should enforce stronger password requirements on the server side.

Recommended improvements include:
- Enforce a minimum password length.
- Reject commonly used and easily guessed passwords.
- Check passwords against known breached-password lists.
- Provide password-strength feedback during registration.
- Apply rate limiting to login attempts.
- Consider enabling multi-factor authentication for sensitive accounts.
- 
Password validation should be enforced by the backend and should not rely only on client-side validation.
